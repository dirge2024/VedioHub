# 项目整体介绍

## 项目定位与完整链路

### Q1：请你先用一两分钟介绍 DoVideoAI

DoVideoAI 是我用 AI Coding 辅助开发的长视频内容理解平台。用户上传课程、会议或操作录屏后，可以给出“生成复习笔记”“提取操作步骤”“核验视频观点”这样的分析目标。系统先把视频整理成带时间轴的语音和关键帧文字证据，再按目标检索相关片段，由 Planner、Executor 和 Critic 完成任务拆解、产物生成和逐结论校验，最后返回可以回到原视频时间点核验的结构化结果。

这个项目有两条主线。前半段解决长视频文件大、处理慢、外部服务不稳定的问题，所以有分片续传、RocketMQ、Redisson、限流和重试。后半段解决 AI 输入不完整、长上下文干扰和结果缺少证据的问题，所以有 VideoContext、混合检索、受控 AgentLoop 和 Checkpoint。我的核心思路是先把视频变成可复用的证据资产，再让 Agent 在证据边界内完成目标驱动分析。

### Q2：从用户上传视频到拿到结果，完整流程是什么？

用户先初始化上传任务，前端把视频按不超过 5MB 的分片并发上传。后端用 uploadId 记录任务归属，分片先写入 MinIO，再把成功序号记入 Redis。全部分片完成后，前端调用合并接口，后端按序读取分片形成完整文件，在合并过程中计算内容 MD5，保存视频资产并清理临时分片。

用户提交分析目标后，系统先做用户级和全局限流，再以“内容指纹 + 目标摘要”判断是否已有相同任务在运行。通过后把 mediaId、内容指纹和 userGoal 投递到 RocketMQ，接口返回 202。消费者拿到 Redisson 锁后先查 Checkpoint；没有 VideoContext 才并行执行 ASR 和 OCR，之后生成 5 分钟 Chunk、摘要、关键词和 Embedding。系统先按 userGoal 粗召回相关证据，再执行 Planner、Executor、Critic。Critic 不通过时，系统根据缺失任务、无证据 Claim 和时间戳补充上下文，最多进行有限轮修正。最终结果和 Checkpoint 写入 MySQL，Redis 保存热数据，前端通过 SSE 接收阶段变化并展示结论、证据和后续追问入口。

### Q3：这个项目真正解决的用户问题是什么？

项目起点是学校课程回放。视频往往一两个小时，用户真正想要的并不是一段泛泛摘要，而是快速得到某种可使用的产物，例如复习笔记、会议待办、操作手册，之后还能点击证据时间戳回看原片段，或者围绕同一视频继续追问。

因此我把用户价值分成三层：稳定上传让长视频能进来；VideoContext 和检索让相关证据能被找到；AgentLoop 让不同目标能生成不同结构化产物。前端展示执行计划和轨迹只是辅助信息，真正的产物价值是结论能核验、任务能恢复、同一视频可以持续复用。

### Q4：项目里最难的部分是什么？

工程上最难的是长耗时链路的可靠性。上传、FFmpeg、ASR、OCR、Embedding 和 LLM 任何一步失败，都不能让用户从头重来，也不能因为 MQ 重投产生重复调用。Agent 上最难的是产出质量：模型需要看到完整且相关的证据，生成的每条结论还要能回到原始视频核验。

所以我的设计重点一直是边界。MQ 负责重新调度，Redisson 控制同一内容和目标的并发执行，数据库和状态负责最终幂等，Checkpoint 决定从哪里继续；Planner 负责拆任务，Executor 负责按证据生成，Critic 负责找出缺口，程序负责预算和终止。把这些职责分清之后，整条链路才能闭环。

### Q5：ASR、OCR、Embedding 和 LLM 分别怎么选？

我的选型原则是中文视频效果、成本、接入复杂度和结果可追溯性。ASR 当前通过托管接口调用 TeleSpeechASR，并按 60 秒切片获得稳定的分钟级时间范围；OCR 使用本地 Tesseract，适合字幕、PPT 和代码文字，复杂图表不是它的能力边界。Embedding 使用 BGE-M3，负责用户目标和 Chunk 摘要的语义相似度。Planner、Executor、Critic 通过 LangChain4j 接入 OpenAI 兼容网关上的 DeepSeek 系列模型。

这四类能力都被封装在各自边界里。ASR 或 OCR 单路失败可以保留另一条证据；Embedding 或 Qdrant 不可用可以回退本地排序；LLM 输出必须经过结构和证据校验。这样更换模型时主要影响适配层和版本缓存，不需要重写 VideoContext、Agent 状态和业务流程。

### Q6：主要数据分别保存在哪里？

MySQL 保存用户、视频资产、最终结果、失败任务和 Agent Checkpoint，是业务事实与恢复真源。MinIO 保存完整视频和关键帧证据。Redis 保存分片上传进度、活动任务标识、限流状态、Checkpoint 热缓存、Trace 和短期用户反馈。Qdrant 保存按视频隔离的 Chunk 向量，向量命中后仍然回到 Checkpoint 中的原始 VideoSegment 取证。

这里最重要的不是用了几个存储，而是冷热和事实边界：Redis 丢失只应该影响性能，不能让用户任务永久丢失；Qdrant 不可用只影响语义召回，不能阻断分析；大型二进制对象不进入 MySQL；最终状态不能只放缓存。

### Q7：大量代码由 AI 辅助生成，你自己的价值在哪里？

AI 帮我缩短了编码和方案搜索时间，但它不会替我确定业务边界。比如它可以列出线程池、MQ、分布式锁和向量库，但是否值得引入，要结合任务时长、失败成本、现有 Redis、视频复用粒度和用户目标来判断。当前上传链路为什么使用 uploadId、分析幂等为什么同时包含内容指纹和 goalDigest、Critic 失败后为什么必须改变上下文，这些都需要我先把业务矛盾想清楚。

我的工作方式是先让 AI 展开候选方案，再用代码、官方接口和实际链路验证。AI 生成实现后，我重点检查状态推进顺序、异常是否被吞、重复请求会不会产生副作用、缓存是否被当成事实来源。这个项目能体现的不是我手写了多少行代码，而是我能不能识别 AI 代码里看起来合理但业务上不闭环的部分。

### Q8：当前项目还有哪些不足？

第一，当前是受控工作流，工具边界固定，不适合需要开放互联网搜索和长时间自主探索的任务。第二，OCR 主要提取文字，不能完整理解动作、图表和复杂公式。第三，Claim 校验包含确定性文本匹配和 LLM Critic，仍然不能证明每个结论在语义上绝对正确。第四，离线评测只有 4 个样本且尚未跑出可信数据，用户反馈也没有形成长期数据闭环。

这些边界不会推翻项目价值。当前目标是把长视频分析做成可检索、可校验、可恢复的后端工作流。等视觉理解需求、样本规模或多工具任务真正增长后，再分别引入视觉模型、扩充评测集和更通用的工具编排。

# 设计 Planner-Executor-Critic 工作流，实现任务拆解、Claim级证据校验、反馈重执行与结构化输出

## 背景和核心矛盾

### Q1：为什么一次大模型总结不够？

一次 Prompt 可以生成一段文字，但用户目标并不固定。同一个视频可能要课程笔记、会议纪要、操作步骤或观点核验。把所有要求直接塞进一次 Prompt 后，模型漏掉哪项要求、使用了哪段证据、为什么得到某个结论，程序都无法判断；结果不合格时也只能整篇重写。

我需要解决的是目标执行的可控性，所以把过程拆成计划、执行和校验。Planner 把目标变成可检查的任务，Executor 逐项完成并绑定证据，Critic 把缺失要求和无证据结论变成下一轮可执行反馈。这样后端能够知道任务进行到哪里、为什么失败、应该补哪部分。

### Q2：为什么它算 Agent，而不是连续调用三次 LLM？

判断标准不在调用次数，而在系统是否围绕目标维护状态并根据反馈改变后续动作。当前 Agent 保存 userGoal、Plan、检索上下文、AnalysisResult、CriticResult、轮次和预算；Critic 不通过后，程序会判断是补计划、补证据还是只重写结构，再决定是否进入下一轮。

我会把它描述为受控 Video Agent Workflow。模型负责开放式理解和判断，程序负责工具边界、状态、预算、重试与终止。它没有完全自治，但在视频分析这个确定业务里已经具备目标、计划、工具、反馈和循环。

## 状态、职责与执行流程

### Q3：Planner、Executor、Critic 和确定性程序分别负责什么？

Planner 只负责理解目标并生成 1 到 5 个可验证任务，不能查询视频之外的信息。Executor 读取 Plan 和相关 VideoContext，生成固定结构的标题、结论、证据和建议。Critic 检查目标覆盖、任务完成度、证据支持和结构完整性，并返回缺失任务、无证据 Claim 和需要补充的时间戳。

确定性程序承担模型不适合承担的边界：限制任务数量，校验结构字段，检查证据时间戳与来源，决定是否刷新上下文，记录 Checkpoint，统计 Token，并在预算耗尽时终止。这样即使模型输出不稳定，也不能随意改变系统状态。

### Q4：AgentLoop 的完整执行顺序是什么？

系统先从完整 VideoContext 中按 userGoal 粗召回相关 Chunk，避免 Planner 读取整条长视频。然后加载目标级 Checkpoint：已有合法 Plan 就复用，没有才调用 Planner；Plan 结构不完整会先修复。Executor 按 Plan 生成草稿，每条结论必须绑定证据，草稿先写 Checkpoint，再进入 Critic。

Critic 之后还有程序规则校验。通过就保存结果；未通过则检查反馈类型。遗漏用户要求会触发 Replanner，缺少证据会将 unsupportedClaims 和 requiredTimestamps 拼成新查询，从完整 VideoContext 补充相关片段，结构问题则只需要带着反馈重写。之后进入下一轮，直到 Critic 通过或预算终止。

### Q5：Planner 怎样保证任务可以执行？

Planner 有三条边界。任务必须能由当前视频证据完成，不能生成“搜索互联网评价”这种系统没有工具支持的任务；任务必须足够具体，后续能判断完成与否；任务数量被程序限制在 1 到 5 条，避免把一次视频分析拆成不可控的长计划。

如果 Planner 返回空任务、过长任务或缺少目标理解，系统会调用一次计划修复；Critic 后续发现目标遗漏时，会把 missingRequirements 交回 Planner 修订。修订失败时保留旧计划继续处理，避免一次重规划错误破坏已有结果。

## Claim级证据校验与反馈重执行

### Q6：Claim级证据校验具体校验什么？

Executor 输出的每条 conclusion 都必须有 evidence.claim 原样绑定，同时带时间戳、来源和证据原文。程序先检查时间戳是否落在某个 VideoSegment 中，再根据 source 只到对应 ASR、OCR 或两路文本里查证据内容。文本检查会先做规范化，再进行包含关系和轻量二元组覆盖判断。

这一步能防止模型伪造时间戳、引用不存在的原文，或者输出结论却不说明依据。它仍然不能完全证明“证据一定蕴含结论”，因此后面还有 LLM Critic 判断语义是否越界。面试时我不会把它说成消除幻觉，而会说它把无依据结论变成可检测、可追踪的问题。

### Q7：Critic 不通过后，系统怎样真正改变下一轮？

Critic 必须返回结构化失败原因。missingRequirements 表示计划漏了用户目标，unsupportedClaims 表示结论缺少支持，requiredTimestamps 表示需要回到特定时间范围加载证据，普通 feedback 表示当前证据足够但写法或结构需要修改。

程序只在出现证据缺口时调用检索层。它会把用户目标、失败反馈和无证据 Claim 组成新查询，同时强制加入 requiredTimestamps 附近的 VideoSegment，再与上一轮上下文合并并受字符预算限制。遗漏任务则先修订 Plan。这样第二轮拿到的是新计划或新增证据，不是把同一份 Prompt 再问一次。

### Q8：结构化输出失败、证据不足或两轮后仍未通过怎么办？

模型返回 JSON 不合法时会进行一次严格格式重试；业务字段仍然为空时不会把空对象当作成功结果。缺少关键证据时，系统保留可以确认的部分，对无法确认的 Claim 给出警告，不允许根据常识补齐视频没有的信息。

达到最大轮次后，当前实现保存带警告的最佳结果，同时保留 Critic 反馈供用户查看和修正。调用异常进入 Checkpoint 与 MQ 恢复；预算耗尽属于主动终止，进入 BUDGET_EXHAUSTED，不再重试，因为重试不会改变预算条件，只会继续消耗资源。

## 终止预算、评测和边界

### Q9：为什么不能只设置“最多两轮”？

轮次只能限制循环次数，不能覆盖单次模型调用过慢、上下文过大或模型价格变化。所以系统同时设置最大轮数、最大执行时长、预估 Token 和预估费用。每个关键模型阶段结束后读取当前 Trace 的消耗，任一条件超过上限就终止。

当前默认最多两轮，是因为第一轮生成、第二轮定向修正已经能形成最小闭环。Token 通过字符规则估算，费用依赖真实单价配置，时长检查也只能发生在阶段之间。这些都是第一版可解释的工程约束，不等于精确计费或强制取消已经发出的 HTTP 请求。

### Q10：如何证明 AgentLoop 优于单次 Prompt？

我会固定同一批 VideoContext 和用户目标，比较单次 Prompt、Planner + Executor、Planner + Executor + Critic 三组。结果指标看结构完整率、目标覆盖、时间戳覆盖、证据支持和 Claim 证据支持；过程指标看模型调用次数、平均轮次、耗时、Token 和预算终止次数。

当前仓库提供 4 个最小 Golden Case，覆盖多模态互补、单模态降级和音画冲突，评测入口会走真实 AgentLoop。它现在只是回归框架，还没有实际运行数据，所以面试中只能讲评测设计，不能声称已经达到某个通过率。后续应增加人工标准答案、困难负样本和跨模型回归，避免用同一模型既生成又自证。

# 并行执行 ASR转写 与 关键帧OCR，按时间轴融合语音、字幕及关键帧文本，共同构建多模态 VideoContext

## 背景和核心矛盾

### Q1：纯 ASR 为什么无法支撑视频 Agent？

课程、会议和操作录屏的信息不只存在于语音。老师说“看这个公式”，ASR 只能得到一句指代；代码演示可能不讲解，但屏幕里出现了命令和报错；会议画面可能展示日期和负责人。输入阶段已经丢失的信息，后面换更强模型也无法补回来。

所以我把语音和关键帧文字当作两类独立证据。VideoContext 的作用是把它们统一到时间轴上，让 Planner、检索、Executor 和 Critic 使用同一种证据结构，而不是分别适配 ASR 和 OCR 的返回格式。

## 构建流程与技术选型

### Q2：VideoContext 是怎样完整构建出来的？

消费者先检查视频级 Checkpoint，没有可复用上下文才开始处理。系统建立临时工作目录，并把 ASR 与关键帧 OCR 分别提交到独立有界线程池。语音侧用 FFmpeg 提取并切成 60 秒音频，逐片调用 ASR，形成带起止时间的 transcript。视觉侧用场景变化加 30 秒保底抽帧，相邻图片经过感知哈希去重，再执行 OCR 并把关键帧上传到 MinIO。

两路结束后，系统按 60 秒窗口归并。语音片段按起始时间进入窗口，OCR 按关键帧时间点进入窗口。窗口可以只有 ASR、只有 OCR，也可以同时存在两路证据。最终每个 VideoSegment 保存起止时间、转写、OCR 文本和证据帧，多个 Segment 组成 VideoContext。

### Q3：场景变化检测、保底抽帧和感知哈希分别解决什么？

场景变化检测适合捕捉 PPT 翻页、窗口切换和页面跳转，减少固定频率抽帧产生的大量重复图片。但缓慢板书或长时间静态页面可能一直达不到变化阈值，因此 30 秒没有选中画面时会保底抽一帧。抽帧之后再用感知哈希比较相邻图片，差异很小时跳过 OCR。

这三层分别处理“重要变化及时拿到”“静态内容不能完全漏掉”和“相似图片不要重复识别”。当前阈值是课程视频的工程起点，不是适用于所有视频的行业标准；鼠标移动、动画和镜头抖动仍可能产生噪声。

### Q4：为什么 ASR 固定切成 60 秒？

当前托管 ASR 返回文本，但不能稳定提供句子级时间戳，所以固定切片给每段转写建立最低限度的时间范围。切得过短会让两小时视频产生大量网络请求，增加失败率和重试成本；切得过长会让定位过粗，后续检索和 Critic 很难把结论落到具体片段。

60 秒是请求数量和证据粒度之间的折中。它只能支持分钟级定位，我不会说成句子级精确证据。以后 ASR 能稳定返回句子或词级时间戳时，可以保持 VideoContext 结构不变，只替换更细的 TranscriptSegment。

### Q5：为什么使用 CompletableFuture，而不是再拆两个 RocketMQ Topic？

RocketMQ 负责整个视频分析任务离开 Web 请求线程，ASR 和 OCR 是同一任务内部需要汇合的两个分支。当前没有独立部署和扩缩容诉求，使用 CompletableFuture 配合两个专用线程池就能并行；总耗时接近较慢分支，而不是两路耗时相加。

拆成两个 Topic 后还要增加子任务状态、聚合器、超时收敛、重复消息和一边成功一边失败的协调。当前规模下这些分布式编排成本没有收益。线程池采用有界队列和拒绝策略，避免无上限占用 CPU、网络和内存；等两路需要不同硬件或独立扩容时再拆服务。

## 局部失败、冲突与降级

### Q6：ASR 或 OCR 局部失败时怎样处理？

两条 Future 不直接向外抛出单路异常，而是返回分支结果。ASR 按 60 秒片段隔离失败，OCR 按关键帧隔离失败；单个片段失败不会删除其他成功结果。如果一整条分支失败，系统记录分支缺失并保留另一条证据，只有两路都失败或最终没有任何有效 Segment 才让 VideoContext 构建失败。

Agent 后续只能使用实际存在的证据。只有 OCR 时可以描述画面文字，不能推测讲解；只有 ASR 时可以总结语音，不能声称读取了 PPT。某个目标依赖缺失模态时，应返回部分结果或证据不足，而不是静默降级后生成完整答案。

### Q7：ASR 和 OCR 冲突、音画不同步或卡在窗口边界怎么办？

系统不会让某一路覆盖另一路。ASR 与 OCR 原始文本都会保留，Executor 需要说明结论来自哪种证据；两路明显冲突时应输出“不一致”，Critic 也会阻止把冲突内容包装成确定事实。离线评测里专门保留了上线日期冲突样本。

时间窗口采用左闭右开，刚好位于 60 秒的帧进入下一窗口，避免重复归属。当前没有自动修复所有音画偏移的能力，明显不同步时只能降低时间戳置信度。需要更高精度时可以估计统一 offset，或者接入带句子时间戳的 ASR 后缩小融合范围。

### Q8：为什么不直接使用多模态视频大模型？

端到端视频模型适合短视频和一次性理解，但当前项目强调长视频复用、继续追问和证据追溯。每换一个目标都重新上传整段视频，成本和延迟难以控制；一次性模型回答也不容易沉淀成可检索、可恢复的资产。

ASR + OCR 的链路更长，但结果可以持久化和复用，证据能定位到时间段。代价是 OCR 只能理解文字，复杂图表、动作和非文字视觉语义会漏掉。合理升级方式是对低置信度或强视觉任务定向调用视觉模型，而不是所有关键帧全量调用。

## 指标验证与总结

### Q9：如何证明 VideoContext 比纯 ASR 有价值？

对照组只提供 transcript，实验组提供 ASR + OCR VideoContext，样本重点选择 PPT、代码和操作画面密集的视频。结果看视觉知识点召回、目标覆盖、时间戳覆盖和最终 Claim 证据支持；代价看 OCR 调用数、重复帧比例、构建耗时和上下文长度。

当前代码已经记录 ASR/OCR 调用、分支失败、OCR 帧失败和上下文长度，但没有形成真实实验报告。因此面试中可以讲清验证方法和过程指标，不能编造提升百分比。

# 针对长视频实现分层摘要 + Embedding混合检索，结合 Checkpoint 支持证据按需加载与异常续跑

## 长视频上下文压缩

### Q1：为什么不能把完整 VideoContext 直接交给模型？

两小时视频会产生大量 ASR 和 OCR 文本。每次分析都全量输入会重复消耗 Token，大量无关片段也会干扰模型判断，继续追问时还会反复发送相同内容。长视频 Agent 的关键是让模型看到与当前目标最相关的原始证据。

我采用两层上下文：Chunk 摘要和向量负责定位，原始 VideoSegment 负责生成和校验。摘要是有损压缩，不能作为最终事实来源。最终 Claim 必须回到原始 ASR、OCR 和时间戳作证。

### Q2：分层摘要和混合检索的完整流程是什么？

超过 5 分钟的视频会把连续 VideoSegment 聚合成 5 分钟 Chunk。每个 Chunk 保存原始 Segment、200 字内摘要、关键词和摘要 Embedding。用户目标先生成查询向量，Qdrant 在当前 mediaId 范围内召回候选 Chunk，再与关键词分数融合，当前语义权重 0.7、关键词权重 0.3，最终选择 Top3。

命中后不会直接把摘要交给 Executor，而是展开 Chunk 内原始 VideoSegment，并受 24000 字符上下文预算限制。短视频直接使用原始 Segment，不为几分钟内容额外生成摘要和向量。

### Q3：为什么同时需要关键词和 Embedding？

Embedding 能处理“递归效率”和“递归时间复杂度”这类语义相近但字面不同的表达；关键词更适合 B+树、HashMap、函数名、数字和章节名。单独使用向量可能弱化精确符号，单独使用字符串又容易漏同义表达。

当前关键词匹配很轻，只判断目标是否包含 Chunk 关键词，适合单视频几十个 Chunk 的 Demo。它不是成熟搜索引擎。数据规模和检索要求上升后，可以引入 BM25 和 Reranker，但在有实际召回问题前不需要继续堆组件。

### Q4：Qdrant 或 Embedding 服务不可用怎么办？

Chunk 生成摘要失败时，系统截取原始文本作为退化摘要；Embedding 失败时使用空向量。Qdrant 写入或搜索失败会记录 fallback 指标，并回到应用内已有向量余弦相似度和关键词排序。即使向量也不可用，关键词仍能提供最低限度召回。

这个降级优先保证链路能继续，但质量可能下降，所以不能静默声称与正常检索等价。后续应该把 vectorStoreFallbacks、embeddingFallbacks 和低分命中展示到 Trace 或告警中。

## Agent衔接与检索兜底

### Q5：Planner 和 Critic 分别怎样使用检索？

第一轮先按完整 userGoal 粗召回，让 Planner 在少量相关证据上拆任务。这种顺序成本低，但复杂目标可能有多个意图，粗召回会偏向其中一部分。Critic 发现遗漏任务或无证据 Claim 后，会把 feedback、missingRequirements、unsupportedClaims 和 requiredTimestamps 交给检索层重新查询。

第二轮上下文由三部分合并：上一轮证据、Critic 指定时间附近的 Segment、新查询召回的 Chunk。这样 Critic 反馈真的改变上下文。更复杂的演进是 Planner 每个子任务单独生成查询，但当前最多 5 个任务，第一版没有增加这一层调用成本。

### Q6：摘要漏信息、检索命中错误或 TopK 不够怎么办？

摘要漏信息时关键词和向量可能同时失效，因此 requiredTimestamps 可以绕过摘要，直接加载指定时间附近的原始 Segment。检索命中只是候选证据，不代表结论正确，Executor 仍需绑定原文，Critic 和程序规则再检查证据是否存在。

当前固定 Top3 和字符预算是可控起点，没有低分动态扩大 TopK，也没有相邻 Chunk 自动扩展。面试中应把这两项说成明确改进：当最高分过低或 Claim 无法取证时扩大候选范围，而不是把它包装成已经完整解决。

## Checkpoint状态与恢复

### Q7：Checkpoint 与缓存、幂等和 MQ 重试有什么区别？

MQ 重试解决失败任务有没有再次执行机会，幂等解决重复执行会不会产生副作用，缓存解决相同输入能不能更快读取，Checkpoint 解决任务内部应该从哪个阶段继续。四者处理的是不同问题。

例如 Executor 已经生成草稿，但 Critic 调用失败。MQ 会重新投递任务，目标级锁避免两个消费者同时执行，Checkpoint 让新消费者读取草稿直接从 Critic 继续，Redis 命中只是加快读取；Redis 丢失后仍然可以从 MySQL 恢复。

### Q8：Checkpoint 保存什么，为什么要区分视频级和目标级？

视频级产物只由视频内容决定，包括 VideoContext、5 分钟 Chunk、摘要、关键词和 Embedding，可以被多个分析目标复用。目标级产物由 userGoal 决定，包括 Plan、Executor 草稿、CriticState 和最终 Result，以 goalDigest 隔离。

同一视频生成复习笔记和操作步骤时，可以共享 ASR/OCR 和索引，不能共享 Plan 和结果。这个划分同时服务于继续追问、内容级去重和目标级幂等，避免旧目标状态污染新任务。

### Q9：Checkpoint 怎样持久化，Redis 挂了怎么办？

写入时先把序列化产物和阶段 upsert 到 MySQL，事务提交后再更新 Redis Hash；读取时先查 Redis，缓存缺失或内容损坏再读 MySQL并回填。Redis 缓存 TTL 是 7 天，MySQL 没有跟着过期，因此用户任务不会因为缓存淘汰永久丢失。

大型视频和关键帧仍在 MinIO，Checkpoint 保存结构化上下文和引用。用户反馈和 Trace 当前主要放 Redis，分别保留 30 天和 7 天，它们还不属于长期业务事实，这是后续评测闭环需要补的地方。

### Q10：不同阶段失败后怎样恢复？

VideoContext 已保存时跳过 ASR/OCR；Chunk 已保存时跳过摘要和 Embedding；Plan 已保存时从 Executor 开始；Executor 草稿已保存而尚未 Critic 时直接校验；Critic 未通过时带着反馈和时间戳补证；Result 已保存时只补最终落库和展示。

ASR 单个切片和 OCR 单帧失败目前主要在一次构建内部隔离，没有持久化到每个切片和帧的 Checkpoint。当前优先保存重算成本最高、边界最清晰的阶段，等超长视频失败率和成本确实上升后再细化。

### Q11：如何避免假完成、并发恢复和版本污染？

Checkpoint 写入把产物和阶段同时持久化，读取终态时还会校验 Plan 和 Result 结构；非法终态不会直接复用。消费者恢复前先获取“内容指纹 + goalDigest”锁，阶段推进同时参考数据库状态，避免两个消费者覆盖同一任务。

当前 Checkpoint 名称没有完整包含 Prompt、Schema 和 Embedding 版本，版本升级的局部失效仍是需要完善的边界。正确策略是 VideoContext Schema 变化重建上下文，Embedding 模型变化重建向量，Executor Prompt 变化只重跑 Executor 之后的阶段。

## 指标验证与总结

### Q12：如何证明检索和 Checkpoint 确实有价值？

检索需要和全量输入做对照，观察相关时间段 Recall@K、最终 Claim 证据支持、输入 Token、上下文长度和总延迟。Checkpoint 通过故障注入验证，在 VideoContext、Chunk、Plan、Executor 和 Critic 后主动失败，检查恢复起点、重复模型调用、最终结果和数据库重复记录。

当前 Trace 已记录检索最高分、召回 Chunk 数、上下文长度、Checkpoint 命中、模型调用和阶段耗时，为验证提供了数据入口。仓库没有实际压测和回归结果，因此只能讲验证方案与已埋指标，不能写“降低多少 Token”或“恢复成功率多少”。

# 采用分片上传与断点续传机制，通过 Redis 记录分片状态，可保障 GB 级视频在弱网环境下的稳定上传

## 背景和核心矛盾

### Q1：为什么普通 Multipart 上传不适合这个项目？

长视频通常几百 MB 到 1GB 以上，一次请求上传完整文件时，网络只要在最后阶段中断，用户就要从头重传。服务端也需要长时间维持连接，失败粒度是整个文件，弱网体验很差。

分片上传把失败范围缩小到单个数据块。成功分片可以保留，网络恢复后只补缺失部分。它增加了上传状态、合并、清理和幂等复杂度，但这些复杂度与长视频场景直接相关。

## 上传协议与完整流程

### Q2：当前分片上传的完整流程是什么？

前端先携带文件名和总分片数初始化任务，后端校验视频后缀、用户身份和分片数量，生成随机 uploadId，并把文件名、总分片数和 userId 写入 Redis，TTL 为一天。前端后续所有请求都携带 uploadId，不以 MD5 直接作为上传任务主键。

上传每片时，后端校验 uploadId 归属、分片序号和 5MB 大小上限，先把对象写入 MinIO，再把成功序号加入 Redis Set。页面刷新或网络恢复后，前端查询 Set，计算总序号与已上传序号的差集，只提交缺失分片。全部完成后调用 complete 接口统一合并。

### Q3：为什么坚持“先写 MinIO，再记录 Redis”？

Redis 中的分片序号代表“对象已经成功落盘”。如果先记 Redis，再写 MinIO，存储失败后 Redis 仍然显示分片完成，合并阶段才暴露缺文件，形成假上传。先落盘再记状态可以让进度记录更可信。

反过来的小窗口是 MinIO 已成功、Redis 写入失败。此时前端会认为该片缺失并再次上传，但对象路径由 uploadId 和 chunkIndex 唯一确定，重传会覆盖同一逻辑分片，不会产生两份业务结果。这是用可重复写换取状态正确性。

### Q4：合并过程怎样保证顺序和幂等？

complete 接口先按 uploadId 获取 Redisson 合并锁，再检查 completedKey；如果该上传已经生成 mediaId，直接返回已有媒体记录。首次合并会校验 Redis Set 数量与 totalChunks 一致，再按照 0 到 N-1 顺序读取 MinIO 分片，写入服务端临时文件，同时计算完整文件 MD5。

完整文件上传到 MinIO 后，系统保存 media_files 记录，写入 completedKey，最后清理分片和 Redis 元数据。这里的 MD5 是合并后内容指纹，用于后续分析去重，并没有与前端预先计算值做完整性对照。

### Q5：为什么分片限制在 5MB、总分片限制为 410？

当前接口限制单片不超过 5MB，总分片不超过 410，因此覆盖约 2GB 视频。5MB 能把弱网重传成本控制在一个较小块，同时避免产生过多 HTTP 请求和对象；410 是当前 Demo 对上传体积和服务端临时合并成本的保护。

这些值不是通用最优参数。更大视频需要调整服务端请求上限、临时磁盘容量和对象存储合并方式，不能只把 totalChunks 配大。简历写“GB 级”成立，面试时不能声称当前支持任意 10GB 文件。

## 异常、并发和安全

### Q6：某个分片失败或上传到 99% 断网，怎样恢复？

失败分片没有写入 Redis Set，其他成功分片不受影响。网络恢复后，前端用原 uploadId 查询已上传集合，只重传差集，然后重新调用 complete。重复上传同一 chunkIndex 也不会让 Set 出现重复序号。

恢复依赖 uploadId 元数据仍在 Redis。当前 TTL 是一天，超过一天后任务会被视为过期，需要重新初始化。这个边界是为了避免临时状态永久占用内存，不会包装成无限期断点续传。

### Q7：两个请求同时合并，或者客户端因超时重复调用 complete 怎么办？

合并锁保证同一 uploadId 同时只有一个线程进入合并区。后续重复请求先查 completedKey，命中后校验媒体归属并返回同一记录，不重复生成文件和数据库记录。锁解决并发执行，completedKey 解决完成后的重复请求，两层职责不同。

如果进程在完整文件上传成功、数据库记录写入前宕机，可能遗留孤立对象；如果数据库成功、completedKey 写入前宕机，再次合并可能重复。当前实现没有跨 MinIO、MySQL 和 Redis 的事务，生产化需要确定性完整文件路径和数据库唯一业务键做补偿。

### Q8：Redis 挂了或者上传元数据过期，MinIO 分片怎么办？

Redis 不可用时当前接口直接失败，不会绕过归属校验继续写入。短时故障恢复后，只要状态还在就能继续。Redis 数据彻底丢失时，当前代码不会扫描 MinIO 自动重建 Set，需要用户重新初始化上传。

正常合并后代码会逐片删除临时对象，但放弃上传或 Redis 元数据过期后的 MinIO 分片还缺少自动生命周期清理。最小改进是给 chunk-uploads 前缀配置对象存储生命周期；当前文档只能把它写成明确边界，不能说已经实现。

### Q9：怎样防止用户访问别人的上传任务？

uploadId 本身不可作为授权。Redis 元数据同时保存 userId，每次查询进度、上传分片和合并都会比较当前登录用户；完成后返回媒体记录时还会再次检查归属。即使用户猜到或拿到别人的 uploadId，也不能读取进度或触发合并。

文件名还会去除路径并限制后缀，uploadId 必须是合法 UUID，分片序号和总数都在服务端校验。这些边界校验比在前端隐藏按钮更重要。

## 指标验证与总结

### Q10：如何证明断点续传真的有效？

我会选固定大小视频，在上传 30%、70% 和 99% 时主动断网或刷新页面，记录恢复后重传字节数、完成时间和最终 MD5。还要测试重复分片、缺失分片、并发 complete、Redis 短暂不可用和 MinIO 写入失败。

结果指标是恢复成功率和最终文件一致性，过程指标是重复上传字节、分片重试次数和合并耗时，代价指标是 Redis 临时状态和 MinIO 临时对象数量。当前仓库没有这组测试结果，因此只保留定性亮点。

# 基于 RocketMQ 异步调度长耗时解析任务，结合 Redisson + MD5 实现内容级去重和消费幂等

## 背景和职责划分

### Q1：为什么视频分析需要 RocketMQ？

分析链路包含 FFmpeg、ASR、OCR、Embedding 和多轮 LLM，耗时远超普通 HTTP 请求。同步执行会长期占用 Web 工作线程，客户端断线还会让任务结果失去承接点。本地线程池能把任务挪出请求线程，但任务仍然只存在当前进程内，服务重启后难以恢复，也不方便独立扩展消费者。

RocketMQ 在这里负责持久化任务入口和重新调度。Web 层只完成参数校验、限流、活动任务登记和消息投递，然后返回 202；消费者独立执行长链路。它不会让视频真正处理得更快，改善的是请求线程占用、失败重投和接入层与计算层解耦。

### Q2：从提交分析到消费者执行，完整流程是什么？

用户提交 mediaId 和 userGoal 后，服务端先校验视频归属，并计算 contentHash 与 goalDigest。系统用两者生成 activeKey，SETNX 成功才继续限流和投递；MQ 发送失败会删除 activeKey，修订任务还会撤销暂存计划。投递成功返回 202，SSE 发布 QUEUED 状态。

消费者收到消息后再次校验字段，以相同的“内容指纹 + goalDigest”获取 Redisson 锁，检查媒体是否仍存在，并记录当前投递次数。已有相同内容和目标的完成结果时可以复用，否则进入 AiService，读取 Checkpoint、构建上下文、执行 AgentLoop并落库。成功后写 completedKey，发布终态并清理活动标识。

## 内容复用与消费幂等

### Q3：为什么幂等 Key 不能只有视频 MD5？

MD5 只描述视频内容。同一视频生成复习笔记和操作步骤，可以复用 ASR、OCR、VideoContext 和 Chunk，不能复用相同 Plan 和 AnalysisResult。如果只按 MD5 加锁，两个不同目标会被错误互斥，甚至返回错误结果。

所以当前分析任务用 contentHash + goalDigest 控制活动任务、分布式锁、完成结果和重试次数。内容指纹负责识别同一视频，goalDigest 负责隔离目标。视频级 Checkpoint 跨目标复用，目标级 Checkpoint 只在相同目标下复用。

### Q4：Redisson 锁、Redis 活动标识和 Checkpoint 各自解决什么？

activeKey 在请求入口拦截同一内容和目标的重复提交，让用户快速得到“任务正在处理中”。Redisson 锁处理 MQ 重投或多实例消费者同时拿到任务的瞬时并发，确保同一目标当前只有一个执行者。Checkpoint 和 completedKey 判断是否已经完成以及从哪里恢复。

锁只能控制持锁期间的执行，不能证明任务历史上从未完成；Redis 标识有 TTL，也不能作为永久事实。因此最终结果和恢复状态进入 MySQL，消费者拿锁后仍要检查业务状态。这比把所有正确性都寄托在一把锁上更稳。

### Q5：为什么用 Redisson，而不是 JVM 锁或手写 SETNX？

JVM 锁只在单实例有效，消费者横向扩容后不同进程之间看不到彼此。项目已经依赖 Redis，使用 Redisson 不增加新的基础设施。相比手写 SETNX，Redisson 提供线程归属和 WatchDog 自动续期，适合处理时长难以预估的 Agent 任务。

当前调用 tryLock 时没有指定固定 leaseTime，因此持锁线程存活期间会自动续期；进程退出后续期停止，锁最终过期。WatchDog 只能降低锁提前失效风险，Redis 故障和长时间 JVM 停顿仍然需要业务状态与幂等写兜底。

### Q6：内容级去重到底节省了什么，是否也实现了文件秒传？

当前最完整的复用发生在分析阶段。两个媒体记录拥有相同 contentHash 时，相同目标可以复用已有 AnalysisResult；不同目标可以复用视频级上下文和索引，避免重复 ASR、OCR 和 Embedding。

上传阶段仍然按 uploadId 保存各自文件，合并后才得到 MD5；media_files 对 content_hash 只有普通索引，没有实现跨用户文件对象秒传。因此简历中的“内容级去重”应解释为视频解析与 Agent 消费去重，不能扩大成对象存储层只保存一份文件。

## 消息失败与状态闭环

### Q7：MQ 重复消费怎样处理？

RocketMQ 的重投可能来自消费超时、进程异常或网络确认丢失，所以消费者必须按至少一次语义设计。重复消息先竞争目标级锁，再检查 completedKey 和 MySQL Checkpoint。已经完成就复用结果，执行到一半就从最近阶段继续，不重新产生完整副作用。

数据库写入、Checkpoint upsert 和确定性缓存 Key 保证重复执行尽量收敛到同一业务状态。锁负责减少并发重入，真正的幂等仍然依赖任务标识、状态检查和可重复写。

### Q8：任务执行失败三次之后怎么办？

消费者用 Redis 记录“内容 + 目标”的执行次数。前两次异常会把状态写为 RETRYING，保留 activeKey，并重新抛出异常交给 RocketMQ 重投。达到三次后停止正常重试，把失败原因写入 failed_analysis_tasks，同时把原消息投递到独立失败主题，阶段改为 DEAD_LETTERED。

这里是项目自建的失败主题和失败任务表，不应说成已经完整搭建 RocketMQ 原生 DLQ 运营体系。管理接口可以查看和重新投递失败任务，但生产环境还需要告警、责任人和防止同一毒消息无限回放的审批规则。

### Q9：MQ 投递成功后，SSE 通知失败会不会导致任务丢失？

不会。MQ 投递成功表示任务已经被 Broker 接收，后续 SSE 只是用户通知。事件发布失败时系统记录日志，不会把任务伪装成投递失败，也不会删除 activeKey让用户重复提交。

前端 SSE 断线会指数退避重连，每次订阅先返回当前 MySQL/Checkpoint 状态，因此用户能恢复当前进度和终态。当前没有持久化完整事件日志，断线期间的每个中间事件可能看不到，但最终业务状态不会依赖 SSE。

### Q10：怎样处理消息积压？

先区分生产突然加快、消费者整体变慢和毒消息反复重试。视频任务最可能的瓶颈是 ASR、OCR 和 LLM 外部依赖，盲目增加消费者可能反而打满模型配额或本机 CPU。应先看队列等待、阶段耗时、重试率和第三方限流，再决定扩容。

如果计算资源允许，可以增加消费者实例和队列数；如果模型平台是瓶颈，应降低生产速率或按配额控制消费。失败任务应及时隔离到失败主题，避免占用正常消费。当前项目有 Trace 和失败表，但没有完整监控大盘，积压治理属于可讲的设计方法而非已验证能力。

## 指标验证与总结

### Q11：如何证明异步和幂等设计有效？

异步化应比较同步接口与任务提交接口的响应时间、Web 线程占用和任务最终成功率；幂等应并发提交同一内容同一目标、制造 MQ 重投并在不同阶段故障，观察模型调用次数、结果记录数和 Checkpoint 恢复点。

当前最新版简历已经删除 60 秒压缩到 50ms 的数字，因此文档不再保留无法复现的漂亮指标。更稳的表达是接口快速返回任务状态、长耗时处理转入 MQ，并通过状态和 SSE 完成业务闭环。

# 基于 Redis 实现令牌桶限流，结合指数退避重试，遏制恶意请求带来的 AI 调用成本并兜底第三方接口抖动

## 限流目标与实现

### Q1：为什么 AI 视频分析必须限流？

一次分析不是一次轻量数据库查询，它可能触发多段 ASR、关键帧 OCR、Embedding、Planner、Executor 和 Critic。恶意点击或脚本请求会同时消耗本机 CPU、模型配额和 Token，最终拖慢所有用户。

限流的位置放在 MQ 投递前，目的是避免无效任务先进入队列再排队烧资源。当前同时限制单用户和全局速率，既防止一个用户独占资源，也保护系统整体容量。

### Q2：当前令牌桶是怎样实现的？

当前没有自己维护 Redis Hash 和 Lua，而是使用 Redisson 的 RRateLimiter。用户维度默认每分钟最多 5 次分析，全局维度每分钟最多 30 次；两个许可都拿到后才能发送 MQ。Redisson 把分布式状态放在 Redis，多实例看到同一配额。

这属于请求级限流，不能精确代表模型 Token。一个 5 分钟视频和两小时视频消耗不同，当前方案只能先挡住请求洪峰。需要严格控制模型预算时，应根据上下文长度预估权重，或者在消费者侧按平台 TPM 再加一层加权配额。

### Q3：为什么选择令牌桶思路，而不是固定窗口或漏桶？

固定窗口在边界处可能连续放过两批请求，瞬时压力高于表面阈值；漏桶强调匀速流出，会让系统空闲时的正常小突发也排队。AI 分析希望限制长期速率，同时允许少量用户在令牌充足时快速提交，因此令牌桶更符合交互体验。

当前参数来自 Demo 容量保护，不是压测得到的最优值。生产环境需要结合模型 TPM、本机 CPU、队列等待和用户等级动态调整，而不是背住“5 和 30”。

### Q4：用户许可拿到了，但全局许可失败或 MQ 投递失败怎么办？

全局许可失败时请求返回 429，用户级已经消耗的许可当前不会补回。这会造成少量配额损耗，但不会超发请求，第一版选择简单和安全。要求更精确时可以先拿全局许可再拿用户许可，或者失败后显式归还。

MQ 投递异常会删除 activeKey并撤销暂存修订，返回任务提交失败。令牌会随着限流器时间自然恢复，不尝试跨 Redis 和 MQ 做分布式事务。真正关键的是不能留下一个永远显示“处理中”但实际没有消息的任务。

### Q5：Redis 不可用时选择放行还是拒绝？

当前限流和活动任务判断都依赖 Redis，异常会导致提交失败，属于 fail closed。对于付费模型调用，这比 Redis 挂掉后无条件放行更安全，因为放行可能造成成本和并发同时失控。

代价是 Redis 故障期间新任务不可用。可以通过 Redis 高可用和明确错误提示降低影响，不需要为了短暂可用性在每台实例里增加无法统一的本地限流器。

## 重试分层与终止

### Q6：第三方 API 重试和 RocketMQ 重试有什么区别？

ASR 和 LLM 内部重试处理短暂网络错误、429 和服务端抖动，保持当前任务上下文不变，等待时间是 1 秒、2 秒，最多三次。它的粒度是一次具体外部调用。整个分析任务仍然失败后，消费者才抛异常交给 RocketMQ 重投；MQ 重试会重新进入消费者并利用 Checkpoint 跳过已成功阶段。

两层不能无限叠加。外部调用重试次数有限，任务级重试也限制为三次，最后进入失败主题。预算耗尽、参数非法和权限错误不属于瞬时故障，不应该交给 MQ 继续重试。

### Q7：为什么使用指数退避，当前方案还有什么不足？

立即重试容易在下游仍未恢复时继续失败，固定间隔会让大量任务同时形成周期性冲击。指数退避让故障持续越久，请求间隔越长，适合短暂网络和限流恢复。

当前退避通过 Thread.sleep 实现，会占用执行线程，而且没有随机抖动；多个任务同时失败仍可能一起醒来。当前并发小可以接受，规模上升后应增加 jitter，或者把长等待交给延迟消息和调度器，避免阻塞工作线程。

### Q8：哪些错误应该重试，哪些应该立即失败？

ASR 当前只对网络异常、429 和 5xx 重试，其他 4xx 直接失败，这个边界比较清楚。LLM 目前对 RuntimeException 统一重试，可能把参数错误、鉴权失败等永久错误也重复三次，是当前实现需要继续细化的地方。

更合理的分类是：超时、连接失败、429、部分 5xx 可重试；鉴权失败、参数错误、模型不存在和内容策略拒绝直接失败；结构化 JSON 解析只做一次格式修复。错误分类比“任何异常都重试”更能防止重试放大。

### Q9：重试会不会造成重复扣费和重复结果？

外部模型请求是否已经成功但响应丢失，调用方通常无法完全确认。对于纯生成接口，再次调用可能产生第二次费用，但不会直接写两条业务结果，因为最终结果按内容和目标进入同一 Checkpoint，数据库使用 upsert 保存阶段。

能传幂等键的第三方接口应传 taskId 或请求摘要；不能支持时，只能通过有限重试、预算统计和业务落库幂等控制影响。这里要区分“业务结果不重复”和“第三方绝不重复计费”，后者当前无法保证。

## 指标验证与总结

### Q10：怎样验证限流和重试不是摆设？

限流测试需要并发使用同一用户和多个用户提交任务，验证用户级与全局阈值、HTTP 429、MQ 实际消息数和 activeKey 清理。重试测试分别模拟超时、429、500、鉴权失败和结构化输出错误，记录调用次数、等待时间、最终阶段和是否进入失败主题。

结果指标看任务成功率和错误分类正确率，过程指标看限流拒绝数、平均重试次数、MQ 重投次数和预算终止次数，代价指标看额外延迟、线程占用和重复 Token。当前代码已经有这些 Trace 入口，但没有正式实验数据，面试中不虚构成功率。

# AI Coding附录

## 开发方法与真实性

### Q1：你怎样使用 AI Coding，而不是把项目完全交给 AI？

我先把需求拆成上传、任务调度、视频感知、检索、AgentLoop 和状态恢复，再让 AI 针对单个模块给候选方案和代码。生成前提供接口、输入输出和异常约束，生成后沿入口、状态、外部调用和失败路径检查，不让 AI 自己决定整个项目方向。

AI 最适合展开方案空间和完成机械编码，我负责判断方案是否符合视频任务的耗时、成本和恢复边界。当前文档里保留上传合并、目标级幂等和 Critic 定向取证这些案例，都是因为它们能说明我没有直接接受第一份答案。

### Q2：你遇到过哪些 AI Coding 问题，怎样发现？

最常见的是编造 API、前后端契约不一致、异常被 catch 后吞掉，以及为了显得先进加入没有业务必要的组件。我的处理方法是优先查当前依赖版本和官方接口，编译或最小调用验证 API，按照状态机走失败路径，并检查每个组件究竟解决哪一个业务问题。

这个项目也留下过典型教训：旧文档把 MinIO composeObject、手写 Lua 令牌桶和前端 MD5 写成当前实现，但代码后来已经变化。面试准备也必须像代码一样以当前版本为准，不能只背历史方案。

### Q3：这项工作最能体现你的什么思考？

我最大的收获是把不确定的智能能力放进确定的工程边界。模型可以负责理解目标、拆任务和判断语义，程序必须负责证据来源、状态推进、并发、预算、重试和终止；缓存和向量库可以失败，用户的最终任务状态必须可恢复、可追溯。

AI Coding 也是同样逻辑。AI 可以生成候选实现，我需要用业务约束、真实代码和验证结果决定它是否成立。能解释为什么做、失败后怎样处理、当前边界在哪里，比堆更多 Agent 名词更重要。
