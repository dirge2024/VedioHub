# DoVideoAI 面试拷打文档：六大亮点重构版

## 项目总览

### Q1：请用两分钟介绍 DoVideoAI

DoVideoAI 是我借助 AI Coding 开发的长视频内容理解平台。用户上传课程、会议或者操作录屏后，可以提出“生成复习笔记”“整理会议待办”“提取操作步骤”这样的目标。系统先把视频转化为带时间轴的语音和关键帧文字证据，再围绕用户目标检索相关片段，由 Planner、Executor 和 Critic 完成任务拆解、结构化生成和逐结论校验，用户还可以继续追问并回到原视频时间点核验证据。

这个项目有两条主线。工程主线解决视频文件大、处理时间长、第三方接口不稳定的问题，所以有分片续传、RocketMQ、Redisson、限流、重试和 Checkpoint。Agent 主线解决单次总结无法适配不同目标、长视频上下文过多、模型结论缺少依据的问题，所以有 VideoContext、分层摘要、混合检索和受控 AgentLoop。

我的核心思路是先把视频加工成可以复用和追溯的证据资产，再让 Agent 在明确的证据、状态和预算边界内完成分析，而不是把完整视频直接丢给模型碰运气。

### Q2：从用户上传视频到拿到分析结果，完整链路是什么？

用户先初始化上传任务，前端把视频拆成不超过 5MB 的分片。后端生成 uploadId，保存任务归属和分片总数；每个分片先写入 MinIO，成功后再把分片序号写进 Redis Set。全部分片完成后，前端统一调用完成接口，后端按照序号读取分片形成完整文件，并在合并过程中计算内容 MD5。

用户提交分析目标后，系统先做用户级和全局限流，再以“视频内容指纹 + 目标摘要”拦截相同任务的重复提交。通过后把任务发送到 RocketMQ，请求接口只返回任务已进入队列。消费者拿到消息后获取目标级分布式锁，并先读取 Checkpoint。

没有 VideoContext 时，系统并行执行 ASR 与关键帧 OCR，再按分钟时间轴融合。长视频随后被聚合成五分钟 Chunk，生成摘要、关键词和 Embedding。系统根据用户目标粗召回相关 Chunk，展开其中的原始证据，执行 Planner、Executor 和 Critic。Critic 不通过时，根据遗漏任务、无证据 Claim 和指定时间段补充计划或证据，最多进行有限轮修正。

最终结果和恢复状态写入 MySQL，Redis 保存热数据，MinIO 保存视频和关键帧，Qdrant 保存 Chunk 向量。前端通过 SSE 接收阶段进度；SSE 断线后可以重新订阅并读取当前状态，业务结果不依赖连接本身。

### Q3：这个项目最难的地方是什么？

工程上的难点是长耗时链路的可靠性。上传、FFmpeg、ASR、OCR、Embedding 和 LLM 任意一步失败，都不能要求用户从头开始，也不能因为消息重投产生多份结果或重复调用全部模型。

Agent 上的难点是结果质量。模型需要看到足够但不过量的证据，每条重要结论还要能定位到原视频。如果 Critic 只返回一句“不通过”，下一轮没有新计划或新证据，循环就只是重复生成。

因此我建立了两个闭环：工程层由 MQ、幂等和 Checkpoint 保证任务能重新调度并从中间恢复；Agent 层由任务拆解、Claim 证据绑定和 Critic 定向补证保证结果能够检查和修正。

### Q4：主要数据为什么放在不同存储中？

MySQL 保存用户、视频资产、最终结果、失败任务和 Agent Checkpoint，是任务状态与恢复的事实来源。MinIO 保存完整视频、上传分片和关键帧。Redis 保存上传进度、活动任务、限流状态、Checkpoint 热缓存、短期 Trace 和反馈。Qdrant 保存按视频隔离的 Chunk 向量。

这里的设计原则是：Redis 丢失只能影响读取速度，不能让用户任务永久丢失；Qdrant 不可用只能让语义召回降级，不能阻断整条分析链路；视频和图片不进入 MySQL；最终任务状态不能只放缓存。

# 一、Planner-Executor-Critic 受控 Agent 工作流

## 定位、选型与完整循环

### Q1：为什么需要 Agent 工作流，为什么选择 Planner-Executor-Critic？

一次大模型调用可以生成一段总结，但同一个视频可能需要课程笔记、会议待办、操作步骤或者观点核验。所有要求都塞进一次 Prompt 后，模型漏了哪项要求、用了哪段证据、为什么得到某条结论，程序无法判断；结果不合格时也只能整篇重写。

我选择 Planner-Executor-Critic，是因为视频分析的主要能力和流程相对固定，真正需要解决的是目标覆盖、证据约束和结果修正。Planner 把目标转成可检查任务，Executor 基于证据完成任务，Critic 把问题转成结构化反馈，后端再决定补计划、补证据还是重写。

ReAct 更适合下一步工具和执行路径高度不确定的开放任务，而我的场景没有必要让模型无限“思考—行动”。Multi-Agent 会增加角色通信、状态一致性和调用成本，当前也没有证据证明多个模型角色优于一个模型配合确定性程序规则。因此我把它定位为受控 Video Agent Workflow：模型负责理解与判断，程序负责状态、工具边界、证据、预算和终止。

### Q2：请用一个具体目标讲清 AgentLoop 怎样执行

假设用户上传两小时的数据结构课程，目标是“整理二叉树核心知识点、遍历规则，并生成复习题”。系统先根据目标和视频 Chunk 做一次粗召回，让 Planner 不必读取整条视频。Planner 形成一到五项任务，例如整理二叉树定义、提取三种遍历规则、总结复杂度和生成复习题。

当前 Executor 在一次模型调用中读取完整 Plan 和召回证据，逻辑上逐项覆盖任务，然后输出标题、结论、证据和建议。这里要讲准确：Planner 确实拆出了多个任务，但第一版没有为每个任务启动一个独立 Executor 或子 Agent，而是让一个受约束的 Executor 完成整份计划，减少调用和状态编排成本。

假设 Executor 得出“前序遍历顺序是根、左、右”，并绑定 32 分钟附近的 ASR 与 PPT 文字。Critic 随后发现“时间复杂度”没有证据，就把该结论放入 unsupportedClaims，并返回需要补充的时间范围。系统把用户目标、Critic 反馈和无证据 Claim 重新组成查询，加载相关原始片段，再让 Executor 只修正被指出的问题。

Critic 通过后保存结果；未通过但达到轮次或预算上限时，保存能够确认的结果并附带警告。这个例子把 Agent 的关键闭环串起来了：目标、计划、执行、证据、反馈、上下文变化和终止。

### Q3：Planner 和 Executor 分别受到哪些约束？

Planner 不是自由发挥。它生成的任务必须能够仅依靠当前 VideoContext 完成，数量限制在一到五项，每项必须是可验证的分析动作。计划为空、目标理解缺失、任务过多或者内容过长时，程序会触发一次计划修复；Critic 发现用户要求遗漏时，再执行 Replan。当前 Plan 只有目标理解和任务列表，没有“语音依赖、视觉依赖”这样的字段，不能把这类设计设想说成已实现。

Executor 受到三层约束。第一是任务约束，结果必须覆盖 Plan；第二是上下文约束，不允许引入 VideoContext 之外的事实；第三是结构约束，必须输出标题、结论、证据和建议。每条结论至少绑定一条包含时间戳、来源和原文的证据。

模型第一次返回非法 JSON 时，系统使用相同任务要求再进行一次严格结构重试。第二次仍无法解析就抛出节点异常，由 Checkpoint 和任务级重试接管，不能返回空对象伪装成功。当前代码没有把第一次原始错误响应长期持久化，因此面试时只讲结构重试，不讲“原始响应已经落库”。

## Claim 校验、反馈重执行与终止

### Q4：Claim 级证据校验到底校验什么？

我把校验拆成三层。第一层是结构绑定：每条 conclusion 都必须有 evidence.claim 与之对应，防止只给一堆引用却不知道支持哪条结论。第二层是证据存在性：程序检查时间戳是否落在真实 VideoSegment，来源是否是 ASR、OCR 或两者，并检查引用文本能否在对应原文中找到。文本会先去除空格、标点并统一大小写，再使用包含关系和轻量二元组覆盖判断。

第三层才是语义支持，由 LLM Critic 判断证据是否足以推出结论、是否遗漏目标或者存在逻辑冲突。前两层是确定性规则，可以稳定拦截伪造时间戳、错误来源和不存在的原文；第三层仍然存在模型误判。因此我不会说 Claim 校验消除了幻觉，而会说它把无依据结论变成了可检测、可追踪和可重试的问题。

Critic 与 Executor 使用同一模型确实可能共享盲区，所以质量不能完全交给模型自检。当前方案通过程序规则兜住结构和证据存在性，再由 Critic 处理语义。质量要求更高时可以换不同 Critic 模型或扩大人工评测集，但第一版不为了 Multi-Agent 形式增加成本。

### Q5：Critic 不通过后，为什么第二轮不是重复生成？

Critic 必须返回结构化失败原因。missingRequirements 表示用户要求或计划任务被遗漏，系统会修订 Plan；unsupportedClaims 表示某条结论没有足够证据，系统会把它重新作为检索查询；requiredTimestamps 表示需要直接加载某个时间范围附近的原始 Segment；普通 feedback 表示证据已经足够，只需要修正结构或表达。

只有出现证据缺口时，系统才调用检索层。新的上下文由上一轮证据、Critic 指定时间附近的 Segment 和新查询召回的 Chunk 合并，并继续受上下文长度预算限制。任务遗漏时先 Replan，纯结构问题则沿用当前上下文重写。

所以反馈重执行的关键不在“多调用一次模型”，而在 Critic 的输出会改变下一轮的计划、查询或证据。上下文没有变化的循环不算有效修正。

### Q6：Agent 怎样保存状态、终止和恢复，如何证明它比单次 Prompt 更好？

AgentState 保存用户目标、Plan、当前 Result、CriticResult 和轮次。Plan、Executor 草稿、CriticState 和最终结果会形成目标级 Checkpoint；视频本身的 VideoContext 和 Chunk 属于视频级 Checkpoint。Executor 草稿已经保存而 Critic 失败时，消息重投可以直接从 Critic 继续。

终止条件不只有最大两轮。系统同时限制执行轮数、阶段间累计时长、预估 Token 和预估费用。任一预算超过上限就进入 BUDGET_EXHAUSTED，不交给 MQ 无限重试。当前时长只能在模型阶段之间检查，不能强行取消已经发出的阻塞请求；Token 是字符规则估算，费用只有配置真实模型单价后才有意义，这些边界需要主动说清楚。

评测上，我会固定相同 VideoContext 和用户目标，对比单次 Prompt、Planner + Executor、完整 P-E-C 三组。结果看目标覆盖、结构完整、时间戳覆盖、证据支持和 Claim 支持；过程看模型调用、平均轮次、耗时、Token 和预算终止。仓库目前只有四个最小 Golden Case 和评测入口，没有足够运行数据，因此只能讲评测设计，不能编造提升比例。

# 二、ASR 与关键帧 OCR 构建多模态 VideoContext

## 感知层设计与完整构建

### Q1：为什么纯 ASR 不够，VideoContext 具体是什么？

课程、会议和操作录屏的信息不只存在于语音。老师说“看屏幕上的公式”时，ASR 只有一句指代；操作演示可能没有讲解，但画面中出现了命令和报错；PPT 还可能展示日期、负责人和关键结论。输入阶段已经丢失的信息，后面换更强模型也补不回来。

因此我把语音和关键帧文字作为两类独立证据。VideoContext 是项目内部定义的统一时序模型，不是某个框架提供的行业标准。它由多个 VideoSegment 组成，每个 Segment 保存起止时间、ASR 转写、OCR 文本和关键帧引用。后续检索、Planner、Executor 和 Critic 只理解 VideoContext，不需要分别适配 ASR、OCR 和 FFmpeg 的原始返回格式。

当前属于 ASR + OCR 的轻量多模态。OCR 能识别字幕、PPT 和代码文字，但不能完整理解动作、图表、表情和复杂公式，所以简历写“语音、字幕及关键帧文本”，不夸大成完整视觉理解。

### Q2：VideoContext 从视频开始怎样完整构建？

消费者先检查视频级 Checkpoint，已有 VideoContext 就直接复用。没有时创建临时工作目录，把 ASR 和关键帧 OCR 分别提交到独立有界线程池，两个分支并行执行，但各自内部仍然按照自己的流程处理。

语音分支使用 FFmpeg 去掉视频画面，把音频编码为 MP3，并按照 60 秒切成多个文件。每个音频文件依次调用托管 ASR，文件序号直接映射为起止时间，例如第二段对应 60 到 120 秒。某个音频片段失败时保留其他成功片段，全部片段都失败才认为 ASR 分支失败。

视觉分支先通过场景变化与 30 秒保底规则抽帧，再做 dHash 去重。保留下来的图片调用本地 Tesseract，使用中英文语言包提取文字；关键帧随后上传 MinIO，失败时退化为原视频时间戳引用。最后系统按 60 秒窗口合并两路结果，形成 ASR-only、OCR-only 或双模态 VideoSegment。

两路分支都失败，或者最终没有任何有效 Segment，VideoContext 才整体失败。工作完成后删除本地音频、图片和 FFmpeg 日志等临时文件。

### Q3：场景变化检测到底是怎么做到的？

这里不是我自己训练一个视觉模型，而是使用 FFmpeg `select` 过滤器提供的场景变化分数。FFmpeg 在解码视频时比较当前画面与前面画面的视觉差异，得到一个归一化的 scene score。当前代码满足三个条件之一就选帧：第一帧必须保留；场景变化分数大于 0.35 时立即选帧；距离上一次选帧已经达到 30 秒时强制保底。

选中的帧使用可变帧率方式输出，`showinfo` 同时在日志里记录每一帧的 `pts_time`。Java 解析这个时间值并换算成毫秒，所以 OCR 文本最终能够回到原视频时间轴。场景检测负责找“可能发生有效变化”的画面，并不负责理解画面内容。

场景检测后还有一层 dHash 去重。系统把图片缩放成 9×8 的灰度图，逐行比较相邻像素亮度，生成 64 位差异哈希；再把当前哈希与上一张图片异或，统计不同位数。汉明距离不超过 5 时认为两张图高度相似，跳过后续 OCR。这样一页静态 PPT 即使被 30 秒保底多次抽到，也不会反复识别。

三层机制分别解决不同问题：scene score 捕捉 PPT 翻页和窗口切换；30 秒保底兜住缓慢板书和静态讲解；dHash 降低动画、光标移动和保底帧带来的重复。0.35 和汉明距离 5 是课程视频的经验起点，不是行业标准。验证时应在 PPT、板书和操作录屏上标注重要页面，比较关键页面召回、重复帧比例、OCR 调用数和漏帧率，再调整阈值。

## 时间融合、并行选型与异常兜底

### Q4：为什么使用 60 秒 ASR 切片和 60 秒融合窗口？

当前托管 ASR 返回文本，但不能稳定提供句子级时间戳。固定切片可以为每段转写建立最低限度的时间范围。切得太短会产生大量网络请求和重试，切得太长会让证据定位过粗。60 秒是第一版在调用数量和定位精度之间的折中，只能保证分钟级定位，不能声称精确到某句话。

融合时，系统用时间戳整除 60 秒得到窗口起点。ASR 片段根据自己的开始时间进入窗口，OCR 关键帧根据画面时间点进入窗口。窗口采用左闭右开，例如恰好位于 120 秒的帧只进入 120 到 180 秒，不会同时属于前后两个片段。

先建立统一窗口再填充两路数据，可以自然保留没有语音但有画面文字的 OCR-only Segment，以及只有语音的 ASR-only Segment。以后换成句子级 ASR 时，可以把 Segment 做细，VideoContext、检索和 Agent 上层接口不需要推倒重写。

### Q5：为什么用 CompletableFuture，而不是再拆两个 RocketMQ Topic？

RocketMQ 负责把整个视频分析任务从 Web 请求线程中解耦；ASR 和 OCR 是一个视频任务内部需要汇合的两个分支。当前没有让两路独立部署和扩缩容的需求，所以使用 CompletableFuture 配合专用线程池即可让总耗时接近较慢分支，而不是两路耗时相加。

如果拆成两个 Topic，就必须增加子任务 ID、分支状态、结果聚合器、超时收敛、重复消息和单边失败协调。当前规模下，这些分布式编排成本没有收益。等 ASR 和 OCR 使用不同硬件、由不同服务维护或者需要独立扩容时，再拆服务和 Topic。

当前也没有使用公共 ForkJoinPool。ASR 使用独立有界线程池控制网络调用，OCR 根据机器 CPU 数量配置有界线程池，队列满时直接拒绝，避免无上限堆积。两路总等待设置超时，超时后取消 Future 并让本次构建失败。

### Q6：两路局部失败、识别错误或者内容冲突时怎么办？

ASR 按 60 秒片段隔离失败，OCR 按关键帧隔离失败；单个片段失败不会删除其他成功结果。一整条分支失败时保留另一条分支，两路都失败才终止。后续 Agent 只能使用实际存在的证据：只有 ASR 时不能声称读取了 PPT，只有 OCR 时不能推测老师讲了什么。

ASR 常见错误是同音字、专有名词和英文缩写；OCR 常见错误是空格、重复字符和复杂版式误识别。清洗文本可以用于检索和生成，但不能覆盖原始证据。原始时间戳和关键帧必须保留，方便 Critic 和用户核验。

如果语音说“周一上线”，PPT 写“周三上线”，系统不让其中一路覆盖另一路，而应该把冲突本身作为结果，并分别给出证据。明显音画不同步时，当前系统只能降低时间定位可信度，无法自动修复所有偏移；后续可以通过抽样估计统一 offset 或使用句子级 ASR 缩小误差。

验证 VideoContext 时，应使用纯 ASR 作为对照，重点选择 PPT、代码和操作画面密集的视频。看视觉知识点召回、目标覆盖、时间戳覆盖和 Claim 支持，同时记录 OCR 调用数、重复帧比例、构建耗时和上下文长度。当前没有正式实验数据，因此不写提升百分比。

# 三、分层摘要、Embedding 混合检索与 Checkpoint

## 长视频检索与 Agent 衔接

### Q1：为什么不能把完整 VideoContext 直接交给模型，分层上下文怎样设计？

两小时视频经过 ASR 和 OCR 后会产生大量文本。每次分析都全量输入会重复消耗 Token，无关片段还会干扰模型对当前目标的判断；用户继续追问时，又要重复发送相同内容。

我的设计是“摘要负责找路，原文负责作证”。系统把连续 VideoSegment 聚合成五分钟 Chunk，每个 Chunk 保存原始 Segment、摘要、关键词和 Embedding。用户目标先和这些压缩信息进行检索，命中后再展开对应的原始 ASR、OCR 和时间戳交给 Agent。摘要是有损压缩，不能直接作为最终事实依据。

短于五分钟的视频直接使用原始 Segment，不额外调用模型生成摘要和向量。长视频最终输入还受到 24000 字符预算限制，候选证据超过预算时跳过后续片段，避免检索后再次形成超长上下文。

### Q2：五分钟分块和关键词、Embedding 混合检索是怎么做的？

VideoContext 按固定五分钟区间聚合。五分钟是当前课程视频场景的工程折中：一分钟块数量太多，知识点容易跨块；十五分钟块命中后又会带入大量无关内容。它不是行业标准，视频类型变化后应该重新评估。

每个 Chunk 先生成摘要和关键词，再用摘要与关键词生成 Embedding。查询时，用户目标也生成向量；Qdrant 先在当前 mediaId 范围内召回候选 Chunk，再和关键词分数融合。当前语义分数权重 0.7，关键词权重 0.3，最终选择 Top3。

Embedding 解决“递归效率”和“递归时间复杂度”这类语义相近但字面不同的问题；关键词补充 B+树、HashMap、函数名、数字和章节名等精确内容。当前关键词逻辑只是轻量包含匹配，适合单视频几十个 Chunk，不等同于成熟全文搜索。跨视频规模增长后才考虑 BM25、OpenSearch 和 Reranker。

### Q3：为什么先检索再 Planner，会不会因为第一次检索不完整导致计划遗漏？

这是当前方案最值得主动解释的取舍。Planner 如果读取完整长视频，成本和干扰都很高；Planner 如果完全不看视频，只根据一句 userGoal 拆任务，又可能生成与视频内容无关的计划。因此第一版先用 userGoal 做目标级粗召回，让 Planner 同时看到用户目标和少量相关证据。

粗召回确实可能偏向目标中的某一部分，所以 Critic 承担第二道纠偏。Critic 发现 missingRequirements 时触发 Replan，发现 unsupportedClaims 时把无证据结论变成新查询，发现 requiredTimestamps 时直接加载相应时间附近的原文。第二轮上下文会合并旧证据、定向时间片和新召回结果。

更完整的方案是先给 Planner 一个轻量视频概览，再让每个子任务生成独立检索查询。但这会增加多次查询和编排复杂度。当前目标任务最多五个，先采用“目标级粗召回 + Critic 定向补召回”的最小闭环。

### Q4：摘要漏信息、TopK 没命中或者向量服务失败怎么办？

摘要漏信息是分层检索的主要风险。第一层通过关键词和向量互补；第二层通过 Critic 的 requiredTimestamps 绕过摘要，直接加载指定时间附近的原始 Segment；第三层把 unsupportedClaims、missingRequirements 和反馈组合成新查询，再召回候选 Chunk。

当前没有实现低分自动扩大 TopK 和命中后自动加载相邻 Chunk，所以不能把这两项说成现有能力。它们是明确的升级方向：当最高分低于阈值或者知识点经常跨 Chunk 时，再扩大候选范围。

Embedding 调用失败时返回空向量，Chunk 仍然保留摘要和关键词；Qdrant 写入或查询失败时，系统回退到应用内余弦相似度与关键词排序；向量也不可用时仍可使用关键词。摘要模型失败时，截取原始文本作为退化摘要。这些降级保证任务能够继续，但检索质量可能下降，因此 Trace 会记录降级次数。

## Checkpoint 持久化与异常续跑

### Q5：Checkpoint 与 MQ 重试、幂等和缓存有什么区别，保存哪些内容？

RocketMQ 重试解决失败任务有没有再次执行机会；幂等解决重复执行会不会产生重复副作用；缓存解决数据能不能更快读取；Checkpoint 解决任务内部应该从哪个阶段继续。四者职责不同。

Checkpoint 按复用范围分两类。视频级产物包括 VideoContext、五分钟 Chunk、摘要、关键词和 Embedding，只由视频内容决定，可以跨目标复用。目标级产物包括 Plan、Executor 草稿、CriticState 和最终 Result，由 userGoal 决定，以 goalDigest 隔离。

同一视频生成复习笔记和操作步骤时，可以共享 ASR、OCR 和索引，不能共享 Plan 和结果。用户继续追问时会形成新的目标级状态，但不需要重新上传或重新构建视频级产物。

### Q6：Checkpoint 怎样持久化，不同阶段失败后怎样恢复？

MySQL 是 Checkpoint 的恢复真源，Redis 是七天热缓存。写入时先在事务中 upsert 产物和阶段，事务提交后再更新 Redis；读取时先查 Redis，缓存不存在或者内容损坏再读 MySQL 并回填。因此 Redis 丢失只影响速度，不会让用户任务永久丢失。

VideoContext 已保存时跳过 ASR/OCR；Chunk 已保存时跳过摘要和 Embedding；Plan 已保存时从 Executor 开始；Executor 草稿已保存而 Critic 尚未完成时直接从 Critic 继续；Critic 不通过时带着反馈与时间戳补证；Result 已保存时直接恢复最终结果。

当前 ASR 单片和 OCR 单帧主要在一次构建内部隔离，没有为每个片段持久化 Checkpoint。第一版优先保存重算成本最高、阶段边界最清楚的产物，等超长视频的局部失败成本真正上升后，再细化到分片级恢复。

状态与产物需要一起保存，不能只写“PLAN_COMPLETED”却没有 Plan。当前数据库写入后再更新缓存，减少假完成；恢复时还会验证 Plan 和 Result 的结构。Prompt、VideoContext Schema 和 Embedding 模型升级后还存在版本失效问题，正确做法是按影响范围局部重建。当前 Key 没有完整编码所有模型与 Prompt 版本，这是明确边界。

验证检索和 Checkpoint 时，一边做全量输入与混合检索对照，观察 Recall@K、证据支持、Token 和延迟；另一边在 VideoContext、Chunk、Plan、Executor 和 Critic 后故障注入，检查恢复起点、重复模型调用和最终结果。当前 Trace 已提供检索分数、上下文长度、Checkpoint 命中和阶段耗时入口，但还没有正式实验结果。

# 四、分片上传与断点续传

## 上传协议、状态与合并

### Q1：为什么普通上传不适合长视频，当前完整流程是什么？

长视频通常几百 MB 到数 GB。一个 HTTP 请求上传完整文件时，网络在最后阶段中断，用户仍然要从头重传，服务端也需要长时间维持连接。分片上传把失败粒度缩小到单个数据块，已经成功的部分可以复用。

前端先提交文件名和分片总数初始化任务。后端校验视频类型、用户和分片数量，生成随机 uploadId，并把文件名、总分片数和 userId 保存到 Redis，TTL 为一天。前端随后携带 uploadId、分片序号和总数上传每一片。

后端校验分片不为空、不超过 5MB、序号范围正确且任务属于当前用户，然后先把分片写入 MinIO，再把成功序号加入 Redis Set。网络恢复后，前端查询 Set，只重传缺失序号。所有分片成功后，前端统一调用 complete，后端顺序合并、计算 MD5、保存视频资产并清理临时状态。

### Q2：为什么使用 uploadId 管上传，MD5 在哪里发挥作用？

当前上传任务主键是服务端生成的 uploadId，不是前端提前计算的整文件 MD5。这样初始化不需要让浏览器先完整读取 GB 级文件，也避免把用户提供的哈希直接当作任务授权和唯一身份。

完整 MD5 在服务端合并分片时通过 DigestOutputStream 一边写文件一边计算，不需要再次扫描整个文件。得到的 contentHash 用于后续视频内容识别、解析结果复用和 Agent 任务幂等。

因此当前能力是“合并后内容级解析去重”，不是上传前跨用户秒传。代码也没有前端分片 MD5 与服务端重算对比，不能讲双端完整性校验。现有完整性主要依赖分片数量、顺序读取和对象存储写入成功；需要更强校验时再增加分片哈希或客户端整文件哈希。

### Q3：为什么先写 MinIO 再写 Redis，合并如何保证顺序和幂等？

Redis Set 中的序号代表“这个分片已经成功落盘”。如果先记 Redis 再写 MinIO，存储失败后 Redis 仍显示完成，直到合并阶段才发现缺文件。先写 MinIO 再记账时，即使 MinIO 成功但 Redis 写入失败，前端只会重传同一序号；对象路径由 uploadId 和 chunkIndex 确定，重传覆盖同一逻辑分片。

complete 接口先按 uploadId 获取 Redisson 合并锁，再检查 completedKey。已完成就校验媒体归属并返回原记录。首次合并先确认 Set 数量等于 totalChunks，再按 0 到 N-1 顺序把 MinIO 分片写入本地临时文件，同时计算 MD5。随后上传完整文件、写媒体记录、保存 completedKey，最后清理分片。

锁解决并发 complete，completedKey 解决完成后的重复请求。当前不是使用 MinIO composeObject 原地合并，而是服务端临时文件顺序合并；这会消耗本地磁盘和网络 IO，但逻辑更直观，符合当前 Demo 规模。

## 弱网、异常与安全边界

### Q4：上传到 99% 断网、Redis 故障或合并中宕机会怎样？

上传到 99% 断网后，成功分片仍在 MinIO，序号仍在 Redis。前端通过原 uploadId 查询已上传集合，只补最后的差集。恢复依赖任务没有超过一天 TTL，过期后需要重新初始化，不能描述成无限期续传。

Redis 暂时不可用时当前接口直接失败，不绕过任务归属和状态校验。Redis 数据彻底丢失后，当前不会扫描 MinIO 重建上传 Set，只能重新初始化。正常合并会逐片清理，但放弃上传或 Redis 元数据过期可能遗留临时对象，生产环境应该给 `chunk-uploads/` 前缀配置生命周期清理。

MinIO 完整文件已上传但数据库写入前宕机，可能留下孤立对象；数据库写入成功但 completedKey 写入前宕机，再次调用可能重复合并。MinIO、MySQL 和 Redis 之间没有分布式事务。更稳的生产方案是确定性完整文件路径、数据库唯一业务键、定时扫描和补偿，不需要为上传链路直接引入分布式事务。

### Q5：怎样防止越权、并发滥用和不合理的大文件？如何验证断点续传？

uploadId 不是授权凭证。Redis 元数据同时保存 userId，查询进度、上传分片和合并都会校验当前用户；完成后读取媒体记录还会再次校验归属。文件名会去除路径并限制视频后缀，uploadId 必须是 UUID，分片序号、总数和大小都由服务端验证。

当前单片不超过 5MB，总分片数不超过 410，覆盖约 2GB 文件。这些值是对请求数量、本地临时磁盘和 Demo 资源的保护，不是 MinIO 的通用硬限制，也不能声称支持任意 10GB 视频。大文件需求出现后，需要同时调整上传协议、磁盘预算和对象存储合并方式。

验证时应在 30%、70% 和 99% 主动断网，检查恢复后重传字节数和最终 MD5；同时测试重复分片、缺失分片、并发 complete、Redis 短暂不可用和 MinIO 写入失败。没有这些真实数据时，只保留“弱网下只补缺失分片”的定性结果。

# 五、RocketMQ 异步调度与 Redisson + MD5 幂等

## 异步选型与任务入口

### Q1：为什么需要 RocketMQ，而不是本地线程池、Kafka 或 RabbitMQ？

视频分析包含 FFmpeg、ASR、OCR、Embedding 和多轮 LLM，耗时远超普通 HTTP 请求。同步执行会长时间占用 Web 工作线程，客户端断线后任务也缺少独立承接点。本地线程池只能把任务移出请求线程，任务仍然存在当前进程，服务重启后难以恢复，也不方便独立扩展消费者。

RocketMQ 在这里负责持久化任务入口和失败重投。Web 层只做归属校验、活动任务登记、限流和消息投递，然后返回任务已接收；消费者独立处理长链路。它不会让视频处理本身变快，改善的是请求线程占用、任务承接和失败重新调度。

Kafka 更适合日志和大规模流处理，当前项目不需要它的吞吐优势；RabbitMQ 也能完成任务队列，但项目后续需要任务重试和失败主题，RocketMQ 与现有 Java 技术栈更贴合。这个选型不是说 RocketMQ 全面优于其他 MQ，而是当前业务特征与已有学习成本下的取舍。

### Q2：从用户提交分析到消费者完成，完整流程是什么？

用户提交 mediaId 和 userGoal 后，服务端先校验视频归属，读取合并阶段生成的 contentHash，并计算 goalDigest。系统使用两者生成 activeKey，通过 SETNX 拦截正在执行的相同任务；随后获取用户级和全局配额，通过后发送 RocketMQ。

消息投递失败时删除 activeKey，修订任务还会撤销暂存计划，避免用户看到一个永远不会执行的“处理中”任务。投递成功后发布 QUEUED 事件，接口返回的是任务已进入队列，不是业务完成。

消费者校验消息后，使用 contentHash + goalDigest 获取 Redisson 锁，检查视频是否仍存在，再记录本次执行次数。已有同内容同目标的完成结果时尝试复用；否则读取 Checkpoint，构建必要上下文并执行 AgentLoop。成功后写 completedKey、保存结果并发布终态。

## 幂等边界、重试与用户状态

### Q3：为什么幂等 Key 不能只有 MD5，activeKey、锁和 Checkpoint 各自解决什么？

MD5 只描述视频内容。同一视频生成课程笔记和操作步骤，可以复用 VideoContext 和 Chunk，不能复用相同 Plan 和最终结果。如果只按 MD5 加锁，不同目标会被错误互斥，甚至复用错误产物。

因此任务级 Key 使用 contentHash + goalDigest。activeKey 在请求入口拦截相同任务重复提交；Redisson 锁处理 MQ 重投或多实例消费者的瞬时并发；completedKey 判断相同内容和目标是否已经完成；Checkpoint 判断任务内部从哪里继续；MySQL 保存最终状态。

锁只能约束持锁期间的并发，不能证明任务历史上从未完成；Redis Key 有 TTL，也不能作为永久事实。真正的消费幂等来自稳定业务 Key、状态检查、Checkpoint 和可重复写共同收敛，而不是单独依赖一把锁。

### Q4：为什么使用 Redisson，WatchDog 怎样工作，能保证绝对安全吗？

JVM 锁只在单实例有效，消费者扩容后不同进程无法互斥。手写 SETNX 还需要自己处理锁值归属、原子释放和过期续期。项目已经依赖 Redis，因此使用 Redisson 能直接获得分布式锁和 WatchDog。

当前获取锁时没有指定固定 leaseTime。持锁线程存活期间，WatchDog 会周期性延长锁过期时间，适合时长难以预估的视频 Agent 任务；进程退出后续期停止，锁最终过期。释放前还要检查当前线程是否持有锁，避免误删其他线程重新获得的锁。

WatchDog 只能降低锁在任务处理中提前过期的风险，不能提供业务上的“绝对一次”。Redis 故障、长时间 JVM 停顿和进程崩溃仍可能导致重新执行，因此数据库状态、Checkpoint 和幂等写才是最终兜底。

### Q5：重复消费、执行失败三次和失败消息分别怎么处理？

RocketMQ 按至少一次语义设计，消息可能因为消费异常或确认问题被重新投递。重复消息先竞争目标级锁，再检查 completedKey 和 MySQL Checkpoint。已经完成就复用结果，执行到中间阶段就从最近 Checkpoint 继续。

消费者使用 Redis 记录“内容 + 目标”的执行次数。前两次异常会保留 activeKey，把阶段写成 RETRYING，并重新抛出异常交给 RocketMQ。达到三次后停止普通重试，把失败原因写入失败任务表，再将原消息投递到项目自建的失败主题，任务阶段改成 DEAD_LETTERED。

这里必须讲准确：当前是自建失败主题与失败记录，不是完整的 RocketMQ 原生 DLQ 运营体系。管理端可以查询和重新投递失败任务，但生产环境还需要告警、责任人和防止毒消息无限回放的审批规则。预算耗尽会进入独立终态，不参与普通 MQ 重试。

### Q6：SSE 断开、消息积压或视频被删除时，业务状态怎么闭环？

SSE 只是通知通道，MQ、MySQL 和 Checkpoint 才是业务状态。前端断线后指数退避重连，重新订阅时先读取当前状态，所以可能错过某些中间事件，但不会丢最终结果。旧文档中的三秒轮询已经过时，不能继续使用。

消息积压时先判断是生产突增、消费者变慢还是毒消息重试。视频任务常见瓶颈是模型配额和本机 CPU，盲目增加消费者可能进一步打满下游。应先看队列等待、阶段耗时、失败率和第三方限流，再决定增加消费者、限制生产速率或隔离失败任务。

消费者执行前和完成后都会检查视频是否仍存在。用户在分析期间删除视频时，系统清理运行时产物并停止继续发布有效结果。验证这条亮点时，应并发提交同内容同目标、制造 MQ 重投和阶段故障，观察模型调用次数、结果记录数、恢复点和最终状态，而不是沿用旧文档中没有重新验证的 60 秒到 50ms 数据。

# 六、Redis 令牌桶限流与指数退避重试

## 请求配额与成本保护

### Q1：为什么视频 Agent 必须限流，当前令牌桶怎样实现？

一次分析可能触发多段 ASR、关键帧 OCR、Embedding、Planner、Executor 和 Critic。重复点击或脚本请求会同时消耗 CPU、模型配额和 Token。限流放在 MQ 投递前，避免无效任务先进入队列再消耗资源。

当前没有手写 Redis Hash 和 Lua 令牌桶，而是使用 Redisson RRateLimiter。用户级默认每分钟最多五次，全局默认每分钟最多三十次；两个许可都成功后才发送 MQ。用户维度防止单人独占，全局维度保护系统总容量，多实例共享 Redis 中的同一配额。

这属于请求级限流，不等价于 Token 限流。五分钟视频和两小时视频的成本不同。需要严格控制模型 TPM 时，应根据视频时长和上下文长度估算权重，在消费者侧再增加加权配额，而不是把当前请求数包装成精确成本控制。

### Q2：为什么选择令牌桶，两个限流器之间有什么边界问题？

固定窗口在时间边界可能连续放过两批请求，瞬时流量高于配置；漏桶强调匀速流出，系统空闲时的小规模正常突发也会排队。令牌桶限制长期速率，同时允许令牌充足时快速提交少量请求，更符合交互式分析场景。

当前先获取用户许可，再获取全局许可。如果用户许可成功但全局许可失败，用户许可不会归还，会产生少量配额损耗，但不会超发任务。第一版优先保证简单和成本安全；需要更精确时可以调整获取顺序或者显式归还许可。

Redis 不可用时当前选择 fail closed，也就是拒绝新任务。对于付费 AI 调用，这比限流故障后无条件放行更安全。代价是 Redis 故障期间新任务不可用，应通过 Redis 高可用和明确错误提示解决，不需要在每个实例增加无法统一的本地桶。

## API 重试、任务重试与最终失败

### Q3：第三方 API 重试和 RocketMQ 重试有什么区别？

API 内部重试处理一次具体外部调用的短暂异常，保持当前任务上下文不变。ASR 对网络异常、429 和 5xx 最多尝试三次，失败后等待 1 秒和 2 秒；模型结构化输出失败会重新请求一次合法 JSON。它们的粒度是一个 ASR 片段或者一次模型节点。

整个分析任务仍然失败后，消费者才抛异常交给 RocketMQ。MQ 重投会重新进入消费者，并利用 Checkpoint 跳过已完成阶段。两层重试都有限制，避免“每个 API 重试多次 × 整个任务再重试多次”无限放大。

参数错误、鉴权失败、模型不存在、权限不足和预算耗尽不应该重试。当前 ASR 的错误分类比较明确；LLM 调用仍然偏向对 RuntimeException 统一重试，可能把永久错误也重复执行，这是需要继续细化的边界。

### Q4：指数退避解决什么问题，当前实现还有哪些不足？

立即重试很可能在下游尚未恢复时再次失败；固定间隔会让大量任务同时失败、同时醒来，形成羊群效应。指数退避让连续失败后的等待时间逐步增加，给网络、服务和限流窗口留出恢复时间。

当前 ASR 使用 1 秒、2 秒的等待并在第三次失败后结束。等待通过 Thread.sleep 实现，会占用执行线程，而且没有随机抖动；多个任务同时失败时仍可能一起醒来。当前并发小可以接受，规模增大后应加入 jitter，或者把较长等待交给延迟消息与调度器。

旧文档把第三方 API 指数退避完全写成 RocketMQ 的 10 秒、30 秒、1 分钟阶梯延迟，这是两层机制混淆。正确口径是：API 内部做短退避，任务级失败再由 MQ 重投，最后进入项目失败主题。

### Q5：重试会不会重复扣费、重复结果，三次失败后怎么办？

如果第三方模型已经处理成功，但响应在网络中丢失，调用方无法完全确认，重新请求可能产生第二次费用。业务结果通过 contentHash + goalDigest、Checkpoint 和数据库 upsert 收敛到同一任务，不会直接产生两条最终记录，但无法承诺第三方绝不重复计费。

能传幂等键的外部接口应携带 taskId 或请求摘要；不能支持时，只能通过有限重试、预算统计和业务幂等降低影响。这里必须区分“业务结果不重复”和“第三方调用不重复收费”。

达到任务级重试上限后，失败原因进入失败任务表，消息进入自建失败主题，前端得到明确失败状态，后续由管理端决定是否重放。验证时分别模拟超时、429、500、鉴权失败和结构错误，记录调用次数、等待时间、MQ 重投、最终阶段、额外 Token 和线程占用。当前只有 Trace 入口，没有正式实验结果，因此不写虚构成功率。
